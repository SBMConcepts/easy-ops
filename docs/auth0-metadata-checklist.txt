-------------------------------------------------------------------------------
 SECTION 1 — app_metadata (per Auth0 user)
-------------------------------------------------------------------------------
 Stored on the Auth0 user. On a custom-DB connection it is the OFFLINE fallback
 only — the post-login Action overrides role/org from the DB via /api/auth/sync.
 The DB scripts populate these from public.memberships + public.tenants.

 [ ] Key            : role
     Source         : memberships.role (active membership)
     Type           : string enum (owner|admin|manager|supervisor|employee)
     Used by        : post-login.js (fallbackRole), DB scripts
     Required       : Yes (fallback)

 [ ] Key            : org_id
     Source         : tenants.auth0_org_id
     Type           : string (Auth0 org id, e.g. org_xxxxxxxx)
     Used by        : post-login.js (fallback org), DB scripts
     Required       : Yes (fallback)

 [ ] Key            : tenant_slug
     Source         : tenants.slug
     Type           : string
     Used by        : DB scripts (returned for convenience)
     Required       : Optional

 SECTION 2 — Custom token claims (injected by post-login.js)
-------------------------------------------------------------------------------
 Namespaced claims written to BOTH the ID token and the access token. These are
 the AUTHORITATIVE values consumed at runtime (DB-sourced via /api/auth/sync).

 [ ] Claim          : https://easy-ops-com.vercel.app/role
     Source         : /api/auth/sync response.role (DB memberships.role)
     Tokens         : ID + access
     Read by FE     : AuthContext (getIdTokenClaims -> user.role)
     Read by BE     : auth.ts verifyAuth0Token -> AuthContext.role
     Required       : Yes

 [ ] Claim          : https://easy-ops-com.vercel.app/org_id
     Source         : /api/auth/sync response.orgId (DB tenants.auth0_org_id)
     Tokens         : ID + access
     Read by BE     : auth.ts -> AuthContext.orgId -> db.ts request.jwt.claims
     Required       : Yes (RLS tenant scoping)

 [ ] Claim          : https://easy-ops-za.vercel.app/permissions
     Source         : /api/auth/sync response.permissions (role_permissions)
     Tokens         : ID + access
     Read by FE     : AuthContext usePermissions()
     Read by BE     : auth.ts (merged with native RBAC permissions[])
     Required       : Yes

 SECTION 5 — Custom DB Connection config (Dashboard -> DB connection -> Settings)
-------------------------------------------------------------------------------
 [ ] DATABASE_URL  : Supabase TRANSACTION-mode pooler URL, port 6543
                     postgresql://postgres.[ref]:[pwd]@aws-[region].pooler.supabase.com:6543/postgres
     Used by       : login.js, get-by-email.js (configuration.DATABASE_URL)

 [ ] AUTH0_DB_CONNECTION_ID
     Location      : Server/deployment environment (not a Vite variable)
     Value         : ID of the shared custom database connection to enable for every new organization
     Behavior      : POST /api/organizations adds this connection with signup and
                     automatic organization membership enabled. The connection name
                     displayed in Auth0 comes from the existing connection itself.

 [ ] AUTH0_ORG_ADMIN_ROLE_ID
     Location      : Server/deployment environment (not a Vite variable)
     Value         : Auth0 Organization role ID that grants delegated full administration
     Behavior      : Applied to EasyOps owner/admin invitations and synchronized
                     after an EasyOps role promotion or demotion. EasyOps itself
                     still authorizes from public.org_members.role.

 [ ] Management API M2M scopes
     Required      : read:connections, create:organization_connections,
                     update:organization_connections, create:organization_invitations,
                     read:organization_member_roles,
                     create:organization_member_roles,
                     delete:organization_member_roles
     Tenant setup  : Enable and configure Auth0 delegated administration, then
                     create the Organization role referenced above. This is a
                     tenant capability, not an enabled-connection setting.

 SECTION 8 — Custom Phone Provider (MFA SMS via Amazon SNS)
-------------------------------------------------------------------------------
 Dashboard: Branding -> Phone Provider -> Custom -> Delivery Method: Text.
 Action source: auth0/actions/custom-phone-provider.js (paste into Provider
 Configuration; trigger is Dashboard-only, not listed in the Actions Library).

 [ ] npm dependency (added in the Provider Configuration editor, not
     package.json): @aws-sdk/client-sns (latest 3.x)

 [ ] Action Secrets (Phone Provider editor -> Secrets panel)
     AWS_ACCESS_KEY_ID      : IAM access key, scoped to sns:Publish only
     AWS_SECRET_ACCESS_KEY  : IAM secret key
     AWS_REGION             : SNS region, e.g. eu-west-1
     AWS_SNS_SENDER_ID      : optional alphanumeric sender id

 [ ] AWS IAM prerequisite: dedicated user/role with an sns:Publish-only policy
     (least privilege) backing the access key pair above.

 [ ] Delivery Method: Text checked; Save (auto-deploys the Action); then
     Send Test Message before relying on it in production.

 [ ] Security -> Multi-factor Auth -> Phone Message: "Use Tenant-level
     Messaging Provider" enabled (if present) and the SMS phone factor enabled.

 [ ] Troubleshooting: Auth0 does not surface delivery success/failure to the
     end user for tenant-level providers -> check tenant logs for
     gd_send_sms / gd_send_sms_failure events.

 SECTION 9 — Flexible Identifiers (phone number sign up / login)
-------------------------------------------------------------------------------
 Dashboard: Authentication -> Database -> Username-Password-Authentication ->
 Attributes tab -> Activate. Configure:
   Email     : Use as Identifier = true (unchanged)
   Phone     : Use as Identifier = true; Allow Signup = Optional/Required per
               your invite policy; Verify phone on signup = true (uses the
               custom phone provider from SECTION 8 to deliver the OTP)
 [ ] Universal Login (not Classic) — required for the phone attribute.
 [ ] Configure Identifier First (Authentication -> Universal Login) — required
     for phone verification on signup.
 [ ] scope 'phone' added to the SPA's authorization request if the ID token
     phone_number claim is ever needed client-side (not currently read).

 Server env (.env.local / deployment — separate from the Action's own AWS
 secrets in SECTION 8, since Express cannot read Auth0 Action secrets):
 [ ] AWS_REGION, AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY : used by
     server/lib/sns.ts to send phone-invitation SMS (POST /api/invitations)
 [ ] AWS_SNS_SENDER_ID : optional alphanumeric sender id

 Migration: supabase/migrations/20260819120000_phone_identifier_support.sql
   invitations.email -> nullable, + phone_number column
   user_credentials.email -> nullable, + phone_verified boolean
   users.email -> nullable (users.mobile_number already existed)
 Custom DB scripts updated: create.js, login.js, get-user.js,
 change-password.js all match by email OR mobile_number now. verify.js is
 unaffected — phone verification never reaches it (Auth0's own OTP flow runs
 before create.js).
 Auth0 Actions updated: post-login.js / post-user-registration.js forward
 event.user.phone_number to /api/auth/sync alongside email.

 [ ] KNOWN LIMITATION: Auth0's native Organization Invitation API is
     email-only. Phone invites (POST /api/invitations with phone_number) do
     NOT use that API — they insert into public.invitations directly and
     send their own link via Amazon SNS (server/lib/sns.ts) to
     {APP_URL}/invite/{token}, landing on src/pages/InviteAccept.tsx which
     hands off to /api/login?organization=... for Universal Login signup.
